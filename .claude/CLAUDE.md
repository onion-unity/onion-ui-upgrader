## Project direction

The goal is to upgrade UGUI `Selectable` navigation without subclassing `Selectable`, because Button, Toggle, Slider, etc. already derive from it. Known limitations being addressed: Explicit navigation doesn't adapt to runtime changes, and Automatic/Horizontal/Vertical can pick unintended targets. Unity's `FindSelectable` considers every Selectable in the scene and scores by `dot / distance²`. Per-group navigation is handled by `NavigationGroup` (see below).

## NavigationUpgrader

`Runtime/Navigation/NavigationUpgrader.cs` is an internal `MonoBehaviour` auto-created at startup (`RuntimeInitializeOnLoadMethod`, `DontDestroyOnLoad`). Each `Update`, at `[DefaultExecutionOrder(-10000)]` so it runs before `EventSystem.Update` (order 0) performs the move, it takes `EventSystem.current`'s selected `Selectable` and, only if that Selectable's mode is Automatic/Horizontal/Vertical, computes its neighbors with its own algorithm and writes them into `navigation` as Explicit (only on the frames listed under "Per-frame cost"). Unity then performs the actual move as usual. When the selection changes, the original navigation is restored, so at most one Selectable is modified at a time and scene data is never changed. Explicit/None Selectables are never touched; the developer's inspector setting is the switch.

- Neighbor rule: lives in `NeighborSearch` (internal struct, pure rect math). The runtime upgrader and the Editor profile preview both use it, so keep all scoring there. Two separate steps:
  - **Detection (filter):** the candidate's **center** must lie beyond the origin's leading edge and within `directionTolerance` degrees, with the angle measured from the origin's rect (0° = center inside the origin's row/column). Using centers keeps 0° truly straight and makes the area exactly drawable.
  - **Scoring:** a generalization of Unity's `dot / distance²`, measured like Unity from the leading edge's **center point** to the candidate's center: cost = `distance / cos(angle)^k`, with `k = alignmentBias × 4`. `k = 1` (bias 0.25) with 90° reproduces Unity's `Selectable.FindSelectable` exactly, including wrap-around (Unity's `-dot × distance²`, generalized by `cos^(k-1)`). This was verified against a port of Unity's code on 160,000 random layout/direction/wrap cases. An earlier rect-based `distance × (1 + w·angle/90)` score did *not* match Unity even at "distance only", because Unity's formula already contains a `cos` factor. Keep this parity when changing the scoring.
- `NavigationProfile`: `directionTolerance` is in degrees (0–90, default 60). `alignmentBias` is 0–1 (0 = distance only, 0.25 = Unity, 1 = strongly prefer same row/column; default 0.25).
- Profile inspector (`Editor/Navigation/NavigationProfileEditor.cs`): default fields, a small right-aligned "Reset" button (90° / 0.25 = Unity's behavior), and a live preview of a fixed example layout.
  - Detection areas and arrows use per-axis colors (left/right vs up/down). Above 45° the horizontal and vertical areas overlap; the overlap is computed with Sutherland–Hodgman polygon clipping and filled with diagonal hatch lines (Cyrus–Beck segment clipping, snapped to a global 6px grid so the pattern is continuous). Without it, each area's boundary line looks like it borders the other area. The user rejected a solid tint for the overlap.
  - Hover focus: the preview box is split into four triangles by its diagonals. Hovering one highlights only that direction (area, lines, arrow, pick); the rest are dimmed and hatches are hidden. With the mouse off the preview, all directions are shown. The user preferred this over the earlier "whichever detection areas contain the mouse" rule. The Unity 6 inspector doesn't forward `MouseMove` to IMGUI, so `CreateInspectorGUI` wraps `OnInspectorGUI` in an `IMGUIContainer` and tracks the mouse with UI Toolkit `PointerMoveEvent`/`PointerLeaveEvent`, calling `MarkDirtyRepaint` only while over the preview rect (cached from the last Repaint).
  - Arrows mimic Unity's Selectable navigation gizmo: a Bezier from the origin's edge in the move direction to the pick's facing edge, with both tangents along the move direction, so two arrows to the same pick never coincide.
  - Button boxes use separate state colors (origin / picked / not picked) that must stay distinguishable from the area colors. The user picks the actual colors; don't restyle them unasked. `Handles.DrawSolidRectangleWithOutline` multiplies by `Handles.color`, so boxes go through `DrawBox`, which resets it to white.
  - Keep inspector text minimal: just the "Preview" header and a one-line swatch legend (Current / Selected / Not selected). The one exception is at the top of the inspector: when the profile is the project-wide one, an Info HelpBox says so, and adds "but the navigation upgrade is off" when it is disabled.

So a separate `SceneView.duringSceneGui` drawer mirrors Unity's arrow style and colors, drawing `NavigationUpgrader.TryResolve` results for upgraded modes and `FindSelectableOnX` for Explicit. It uses the same profiles as the runtime (group profiles, else the project-wide one). Explicit Selectables use purple for left/up and blue for right/down (the user's choice) instead of Unity's orange / yellow. The user rejected bright coral / lime as too hard to see, and darker orange / ochre as not distinguishable from Unity's colors so hand-set links stand out. Like Unity's, arrows of selected Selectables are drawn at alpha 1 and the rest at 0.4, but unlike Unity's, nothing is drawn when no scene object is selected (the user's choice). ## NavigationGroup

`Runtime/Navigation/NavigationGroup.cs` is a public, non-Selectable container component (requires a RectTransform). It only affects upgraded modes and does nothing while the upgrade is off. Explicit slots can't reference groups, and the user decided they don't need to.
- Scope: a Selectable belongs to the nearest enabled group on itself or its ancestors (`ScopeOf`), or to the root (null). Upgraded navigation only considers Selectables under the origin's scope (`IsChildOf`), including those inside its child groups. Groups have no rect of their own at runtime: an earlier version scored each child group as one rect (its RectTransform), which the user dropped because a RectTransform can differ from the area its members actually cover. Groups register themselves in a static list on enable. The component is `[ExecuteAlways]` so this also happens in Edit Mode; without it the list is empty there and the visualizer draws no groups.
- `boundary`: `Contain` (default, the user's choice) stops at the group's edge. `PassThrough` searches the parent scope when nothing is found inside, excluding everything under the group being left. Wrap-around happens inside the current scope first, so a wrapping group never passes through.
- Per-scope search settings (`NavigationUpgrader.SearchIn`), evaluated for each search level (the origin's scope, then each Pass Through parent): `wrapAround` (`NavigationWrap` None/Horizontal/Vertical/Both) is ORed with the Selectable's own wrap (which Unity only honors in Horizontal/Vertical mode) and applies in any mode, but only to that scope, not inherited by child groups. `profile` is the nearest one set on the scope or its ancestors, else the project-wide one.
- Entering a group: when the picked Selectable lies in groups below the search scope, those groups are checked from the outermost inward, and the first group with an entry (`EntryOf`: the remembered `lastSelected` when `rememberLastSelection` is on and it is usable and still under the group, else a usable `defaultSelectable`) wins; otherwise the picked Selectable itself. The result is written into the Explicit slot as a Selectable, so no re-selection happens (which would hit `EventSystem`'s "already selecting" guard). `TryResolve` has an overload that also reports the outermost group each direction enters, for the visualizer.
- `lastSelected` is a non-serialized per-instance property (not static, so nothing to reset for Enter Play Mode without domain reload). The upgrader records every selection change into every group above the selected Selectable, regardless of `rememberLastSelection`, so turning that on at runtime works immediately. Only recorded while the upgrade is on. It survives the group being disabled, which is the point for panels that are closed and reopened.
- `selectOnEnable`: `OnEnable` sets `selectPending` (Play Mode only); the upgrader's next `Update` consumes all pending flags and selects the entry of the last-enabled group that has one, via `EventSystem.SetSelectedGameObject`, before reading the selection. Deferring avoids depending on enable order during scene loads (EventSystem or the default Selectable may not be enabled yet). Flags are consumed even while the upgrade is off, and then nothing is selected. With no entry, nothing is selected (no fallback to the first member).
- `restoreOnDisable` (issue #6, for popups overlaid on a menu that stays enabled; when the menu is disabled instead, its own Remember/Select On Enable already work): `OnEnable` (Play Mode only) stores the current selection as `restoreTarget` unless it is under the group; Select On Enable hasn't acted yet, so this is the opener. `OnDisable` adds the group to the static `pendingRestores` when the option is on and a target exists; `OnEnable` removes it again. Groups disabled while exiting Play Mode stay queued (as destroyed references), so the list is cleared at `RuntimeInitializeLoadType.SubsystemRegistration` for Enter Play Mode without domain reload. Whether the selection is in the group is deliberately not checked there: when a popup B and the popup C opened from it close in the same frame with B first, the selection is still in the active C at B's `OnDisable` (found in Play Mode testing). The upgrader's next `Update` consumes the list even while the upgrade is off (then nothing is selected), picks the most recently disabled group that isn't destroyed and whose target `IsUsable`, and selects that target after Select On Enable, only if `HoldsSelection()` (selection lost per `SelectionRecovery.IsLost`, or under the group) is true (so a script's or a newly opened group's selection wins). Going back past unusable targets makes stacked popups closed together (or nested ones disabled with their parent) land on the outermost opener. Destroyed groups (scene unload, `Destroy`) are null by then and skipped, which is why the check is deferred instead of using `scene.isLoaded`. An unusable target does nothing and leaves it to Selection Recovery.
- Dropped on purpose, for now: anchor Selectables, group-to-group links.

## SelectionRecovery

`Runtime/Navigation/SelectionRecovery.cs` is part of the Navigation upgrade, not its own settings section: `NavigationSettings.recoverSelection` (a checkbox under the profile field, on by default), checked through `NavigationSettings.recoversSelection` (upgrade on **and** the box checked). Its move reading now lives in `UIInput.IsMoving`, shared with the Focus tracker. A separate "Selection Recovery" section, independent of Navigation, was tried and merged in by the user's choice, since recovery only reacts to Move input and the independent mode needed a no-groups branch. It is a plain internal class, not a component: `NavigationUpgrader` owns one instance (so its state is recreated every Play, with nothing to reset when domain reload is off) and calls its `LateUpdate` from its own. It was its own auto-created `MonoBehaviour` only while it needed a GameObject for the stand-in (see below); PlayerLoop injection was considered and not used, since the upgrader is a component anyway.
- Lost selection = `currentSelectedGameObject` is null, inactive in hierarchy, or a Selectable that isn't `isActiveAndEnabled` (input modules don't send events to those, so a disabled selection is as dead as null). A non-interactable selection is not lost, since `Selectable.OnMove` still works.
- Recovery happens on Move input only (the user's choice over immediate), so mouse users aren't disturbed. Move input is read directly from `EventSystem.currentInputModule`: `StandaloneInputModule` via `input.GetAxisRaw` on its `horizontalAxis`/`verticalAxis`, `InputSystemUIInputModule` via `move.action.ReadValue<Vector2>()` (only under `ONION_INPUTSYSTEM`, a `versionDefines` entry for `com.unity.inputsystem`; the asmdef also references `Unity.InputSystem` by name, which Unity ignores when the package is absent). A move is the frame the vector first crosses the module's own threshold, matching when it sends Move: `StandaloneInputModule`'s 0.6 dead zone on the vector length (`BaseInputModule.DetermineMoveDirection`, not per axis), and any nonzero vector for `InputSystemUIInputModule`, which has no dead zone of its own (the action's processors apply one), and nothing when `sendNavigationEvents` is off. Custom input modules are not supported (the user's choice). It runs in `LateUpdate`, after `EventSystem.Update` has already sent that frame's move to the lost selection, so the first move only recovers and doesn't also move; if held, the module's repeat delay then moves on. An earlier version selected the recovery object itself as an `IMoveHandler` stand-in to catch moves generically; the user dropped it because `currentSelectedGameObject` was the stand-in instead of null while waiting, which breaks code that reads the selection, and it swallowed Submit/Cancel. A direction already held when the selection is lost doesn't recover until pressed again.
- Target (the user's choice): last selection if `NavigationUpgrader.IsUsable`; else each still-enabled group the last selection was under (recorded innermost first on selection change, since the Selectable may be destroyed later): `EntryOf(group)`, else its member nearest the last position; else the nearest usable Selectable anywhere. Distance is world-space between RectTransform centers (the last position is refreshed every frame while selected). Nothing is recovered before anything has been selected once.

## Focus (issue #9)

A separate `focus` section of `UIUpgraderSettings` (`Runtime/Focus/FocusSettings.cs`, `FocusSettings : UpgradeSettings`, off by default, `FocusSettings.current` is null while off), independent of Navigation. It tracks the input mode (`InputMode` Navigation/Pointer) and one focused Selectable, published through the public static `UIFocus` (`mode`, `focused`, `modeChanged`, `focusChanged(previous, current)`; reset at `SubsystemRegistration`). Hover never changes the EventSystem selection (the issue explains why "select on hover" was rejected). Highlighting the focus is #10's job, not this section's.
- `InputModeTracker` (internal plain class) is owned by `NavigationUpgrader` like `SelectionRecovery`, because Reveal writes the selection's `navigation`, and a second writer would look like a script change to the upgrader's `IsChangedExternally`. So `NavigationUpgrader.Update` no longer returns early when Navigation is off: it tracks a Selectable while it is upgraded **or** its move is held this frame, and `IsUpgradable` takes the mode separately (the tracked Selectable's `navigation` holds what was applied).
- Frame flow: `Update` (after Select On Enable / Restore On Disable, before the selection is read) switches the mode and applies Continue/Reveal. `LateUpdate` (after `SelectionRecovery`) computes the focus and calls `UIFocus.Set`, so a move's new selection is focused the same frame. Continue From Hover uses `UIFocus.focused` from the last LateUpdate, i.e. what was on screen.
- Mode switches (the user's choices): starts in Navigation. Navigation on the frame Move first crosses the module's threshold (edge, like `SelectionRecovery`; a held move doesn't switch back after the pointer moves), on Submit, and on Cancel only with `cancelSwitchesMode`. Pointer on a pointer position change (not layout movement, not the scroll wheel) or a pointer press / touch began. Navigation wins when both happen in one frame. While off, mode is Navigation and focus is the selection (the user's choice).
- Hover = the nearest Selectable parent of the topmost hit at the pointer position, only if `NavigationUpgrader.IsUsable` (what a click would select). Only in Pointer mode. No pointer while the cursor is locked. The hit is the input module's own raycast of this frame (issue #15; the module raycasts every pointer in `EventSystem.Update`, so a second `RaycastAll` doubled the cost): `UIInput.TryGetPointerHit` reads `InputSystemUIInputModule.GetLastRaycastResult` for the device driving the `point` action (else `Pointer.current`; a touchscreen's `deviceId` finds its touch), and for `StandaloneInputModule` the protected `PointerInputModule.m_PointerData` via reflection (first non-indirect touch's `fingerId`, else the mouse id -1, like the module). If that field is missing (a future uGUI renamed it), `FindHovered` falls back to its own `RaycastAll`. When the app isn't focused, both modules skip processing, so the hover keeps the last frame's hit.
- Switching to Navigation: if the shown focus is the selection, nothing. Else with `continueFromHover` and a usable hover, select it. Else with `revealOnFirstInput` and a selection that isn't lost, hold back this frame's input. This rule is "the selection wasn't shown", slightly broader than the issue's "no hover" (it also covers Continue off with a hover).
- Holding back a move: the selection's navigation is Explicit with all four slots pointing at itself for one frame (`NavigationUpgrader.Hold`). The move is sent and consumed, so the module's repeat delay starts (a held key moves after it), and Slider/Scrollbar don't change value (they only do when `FindSelectableOnX()` is null, so null slots wouldn't work). Holding back a submit: `sendNavigationEvents = false` for that frame, restored in the tracker's LateUpdate. It isn't used for moves, since both modules then skip their repeat bookkeeping and a held move would move on the next frame (checked in the ugui/inputsystem source).
- Input reading is shared in `Runtime/UIInput.cs` (`IsMoving`, `WasSubmitPressed`, `WasCancelPressed`, `TryGetPointerPosition`, `WasPointerPressed`), Standalone and `ONION_INPUTSYSTEM` only.

## Per-frame cost

`NavigationUpgrader` doesn't resolve every frame (issue #14). It resolves only when the neighbors can be used or what was applied no longer fits: the frame a Selectable starts being tracked, the frame a script's change to its `navigation` is adopted, the frame after a `Hold` (otherwise a script's `FindSelectableOnX()` would keep returning the Selectable itself), and every frame `UIInput.IsMoving` is true (a superset of the frames the module sends Move). On other frames the applied navigation is kept as is and not written again, which also avoids the setter's `OnSetProperty` → `DoStateTransition`. Custom input modules (`UIInput.CanReadMove` false) resolve every frame, since their moves can't be read; no input module sends no moves and resolves nothing extra. Trade-off: while idle, a script calling `FindSelectableOnX()` sees neighbors from the last resolve, which may be stale after a layout change; the actual move always resolves first. The applied Explicit value stays visible in the inspector while selected; issue #17 tracks applying it only while a move is held.

Each `Resolve` computes all four neighbors, so work shared by the directions is done once per `Resolve`, in `CollectCandidates`:
- The searchable scopes (`_scopes`: the origin's scope, then each parent reachable through Pass Through, null = root) and each candidate's level in them (`_levels`: the innermost scope it is under, or -1 when it is the origin, not a candidate, or outside every scope). A search at level k considers exactly the candidates at level k, which equals "under scope k but not under the Pass Through group being left". So `IsCandidate` and `IsChildOf` run once per candidate, not per direction and level.
- `origin.transform.worldToLocalMatrix` (`_toOrigin`). Each candidate's local rect is computed at most once (lazily, in `Search`, cached in `_rects`/`_hasRect`) by transforming its world corners with `MultiplyPoint3x4`, so that's 1 native call (`GetWorldCorners`) per candidate.

The visualizer's group boxes (`TryGetBox`, `DrawGroup`) likewise transform corners with a matrix fetched once per group.

## Known limitations

- Residual same-frame lag: Unity's `Selectable.OnMove` searches at the moment of input, inside `EventSystem.Update`. The upgrader now computes in an early `Update` (was the previous frame's `LateUpdate`, which also missed layout rebuilds and end-of-frame destroys). Changes made by scripts that run between it and `EventSystem.Update` in the same frame (order below 0, or order 0 scripts Unity happens to run before the EventSystem) are still missed; e.g. a candidate made non-interactable there can still be navigated to, since `Selectable.Navigate` only checks `IsActive()`. There is no hook at move time without subclassing, and a helper `IMoveHandler` on the Selectable would run after `Selectable.OnMove`.
- Script changes to the selected Selectable's `navigation` are kept: each frame the upgrader compares the current value with what it last wrote (`_appliedNavigation`). If they differ, the new value becomes `_originalNavigation` (and tracking stops if its mode is no longer upgraded), and `Release` doesn't overwrite it. `Navigation.Equals` ignores `wrapAround`, but so does the `navigation` setter (`SetPropertyUtility.SetStruct`), so a wrap-only change can't be made anyway. A script setting exactly the value the upgrader wrote is indistinguishable and treated as unchanged.

## Assemblies and namespaces

- `Runtime/Onion.UI.Runtime.asmdef` and `Editor/Onion.UI.Editor.asmdef` (Editor-only, references Runtime). Both set `rootNamespace` to `Onion`, but code uses per-folder sub-namespaces, e.g. `Onion.UI.Navigation` for `Runtime/Navigation/`.
