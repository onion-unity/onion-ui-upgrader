## Build / test

There are no build scripts, tests, or CI. The package is compiled and verified by opening `../_workspace` (Unity 6000.0.58f2) in the Unity Editor, which references this package through a local `file:` path in `_workspace/Packages/manifest.json`. Git commands must run inside this folder (it is its own repo).

To check that the Runtime code compiles without opening Unity, invoke Unity's bundled Roslyn (`D:/Program Files/Unity/Hub/Editor/6000.0.58f2/Editor/Data/NetCoreRuntime/dotnet.exe` running `.../Data/DotNetSdkRoslyn/csc.dll`) with `-target:library -nostdlib -langversion:9.0`, referencing `.../Data/UnityReferenceAssemblies/unity-4.8-api/mscorlib.dll`, its `Facades/*.dll` and `System*.dll`, `.../Data/Managed/UnityEngine/UnityEngine*.dll`, and `../_workspace/Library/ScriptAssemblies/UnityEngine.UI.dll`, and passing the `Runtime/**/*.cs` files. Put the arguments in a response file (`@build.rsp`) because the paths contain spaces. This only checks compilation; behavior still needs Play Mode in `_workspace`. The Editor code compiles the same way against the Runtime output named `Onion.UI.Runtime.dll`, with output named `Onion.UI.Editor.dll` (for `InternalsVisibleTo`), adding `.../Data/Managed/UnityEngine/*.dll` (which includes the UnityEditor modules; don't also add `Managed/UnityEditor.dll`, it causes CS0433 duplicates) and `../_workspace/Library/ScriptAssemblies/UnityEditor.UI.dll`.

## Project direction

The goal is to upgrade UGUI `Selectable` navigation without subclassing `Selectable`, because Button, Toggle, Slider, etc. already derive from it. Known limitations being addressed: Explicit navigation doesn't adapt to runtime changes, and Automatic/Horizontal/Vertical can pick unintended targets. Unity's `FindSelectable` considers every Selectable in the scene and scores by `dot / distance²`. Per-group navigation is handled by `NavigationGroup` (see below).

## NavigationUpgrader

`Runtime/Navigation/NavigationUpgrader.cs` is an internal `MonoBehaviour` auto-created at startup (`RuntimeInitializeOnLoadMethod`, `DontDestroyOnLoad`). Each `LateUpdate` it takes `EventSystem.current`'s selected `Selectable` and, only if that Selectable's mode is Automatic/Horizontal/Vertical, computes its neighbors with its own algorithm and writes them into `navigation` as Explicit. Unity then performs the actual move as usual. When the selection changes, the original navigation is restored, so at most one Selectable is modified at a time and scene data is never changed. Explicit/None Selectables are never touched; the developer's inspector setting is the switch.

- Neighbor rule: lives in `NeighborSearch` (internal struct, pure rect math). The runtime upgrader and the Editor profile preview both use it, so keep all scoring there. Two separate steps:
  - **Detection (filter):** the candidate's **center** must lie beyond the origin's leading edge and within `directionTolerance` degrees, with the angle measured from the origin's rect (0° = center inside the origin's row/column). Using centers keeps 0° truly straight and makes the area exactly drawable.
  - **Scoring:** a generalization of Unity's `dot / distance²`, measured like Unity from the leading edge's **center point** to the candidate's center: cost = `distance / cos(angle)^k`, with `k = alignmentBias × 4`. `k = 1` (bias 0.25) with 90° reproduces Unity's `Selectable.FindSelectable` exactly, including wrap-around (Unity's `-dot × distance²`, generalized by `cos^(k-1)`). This was verified against a port of Unity's code on 160,000 random layout/direction/wrap cases. An earlier rect-based `distance × (1 + w·angle/90)` score did *not* match Unity even at "distance only", because Unity's formula already contains a `cos` factor. Keep this parity when changing the scoring.
- `NavigationProfile`: `directionTolerance` is in degrees (0–90, default 60). `alignmentBias` is 0–1 (0 = distance only, 0.25 = Unity, 1 = strongly prefer same row/column; default 0.25).
- Profile inspector (`Editor/Navigation/NavigationProfileEditor.cs`): default fields, a small right-aligned "Reset" button (90° / 0.25 = Unity's behavior), and a live preview of a fixed example layout.
  - Detection areas and arrows use per-axis colors (left/right vs up/down). Above 45° the horizontal and vertical areas overlap; the overlap is computed with Sutherland–Hodgman polygon clipping and filled with diagonal hatch lines (Cyrus–Beck segment clipping, snapped to a global 6px grid so the pattern is continuous). Without it, each area's boundary line looks like it borders the other area. The user rejected a solid tint for the overlap.
  - Hover focus: the preview box is split into four triangles by its diagonals. Hovering one highlights only that direction (area, lines, arrow, pick); the rest are dimmed and hatches are hidden. With the mouse off the preview, all directions are shown. The user preferred this over the earlier "whichever detection areas contain the mouse" rule. The Unity 6 inspector doesn't forward `MouseMove` to IMGUI, so `CreateInspectorGUI` wraps `OnInspectorGUI` in an `IMGUIContainer` and tracks the mouse with UI Toolkit `PointerMoveEvent`/`PointerLeaveEvent`, calling `MarkDirtyRepaint` only while over the preview rect (cached from the last Repaint).
  - Arrows mimic Unity's Selectable navigation gizmo: a Bezier from the origin's edge in the move direction to the pick's facing edge, with both tangents along the move direction, so two arrows to the same pick never coincide.
  - Button boxes use separate state colors (origin / picked / not picked) that must stay distinguishable from the area colors. The user picks the actual colors; don't restyle them unasked. `Handles.DrawSolidRectangleWithOutline` multiplies by `Handles.color`, so boxes go through `DrawBox`, which resets it to white.
  - Keep inspector text minimal: just the "Preview" header and a one-line swatch legend (Current / Selected / Not selected). The one exception is at the top of the inspector: when the profile is the project-wide one, an Info HelpBox says so, and adds "but the navigation upgrade is off" when it is disabled.
- Scene view visualization (`Editor/Navigation/NavigationVisualizer.cs`): Unity's own "Visualize" calls `Selectable.FindSelectableOnX`, i.e. Unity's algorithm, and can't be changed without subclassing. So a separate `SceneView.duringSceneGui` drawer mirrors Unity's arrow style and colors, drawing `NavigationUpgrader.TryResolve` results for upgraded modes and `FindSelectableOnX` for Explicit. It always uses the default profile, like the runtime. Explicit Selectables use purple for left/up and blue for right/down (the user's choice) instead of Unity's orange / yellow. The user rejected bright coral / lime as too hard to see, and darker orange / ochre as not distinguishable from Unity's colors so hand-set links stand out. Like Unity's, arrows of selected Selectables are drawn at alpha 1 and the rest at 0.4, but unlike Unity's, nothing is drawn when no scene object is selected (the user's choice). Groups: every active group is drawn as a box around its visible area, computed each repaint as the bounds of its direct member Selectables and its child groups' boxes, plus an on-screen margin (so nested boxes don't overlap). `Contain` is a solid line, `PassThrough` dashed. A move that enters a group points at the group's box instead of the final Selectable. Selecting a NavigationGroup draws its direct members' arrows at full strength; selecting a Selectable in a group draws only that group's direct members (selected at 1, others 0.4); otherwise every Selectable is drawn, as before. Pass Through arrows leaving the group show up naturally as members' arrows. The exception is while a `NavigationProfile` is the active selection: then every arrow is drawn at full strength, since nothing in the scene is selected while editing a profile. It is toggled by a "Visualize" button next to Reset in the Profile inspector (the user's choice), stored in EditorPrefs `Onion.UI.Navigation.Visualize`. The two toggles are mutually exclusive. Turning ours on remembers Unity's Visualize state and turns it off; turning ours off restores it. If Unity's is switched on while ours is on, ours turns itself off (checked in `OnSceneGUI`). Unity's state is the private static `UnityEditor.UI.SelectableEditor.s_ShowNavigation`, accessed via reflection, plus EditorPrefs `SelectableEditor.ShowNavigation`. If a future uGUI renames the field, only EditorPrefs is used, which takes effect only after Unity's editor re-enables.
- Slider/Scrollbar in Automatic mode keep their value axis empty, because they only change their value when `FindSelectableOnX()` returns null.
- Settings: `NavigationProfile` (public ScriptableObject, created from Assets > Create > Onion/UI/Navigation Profile) holds the scoring parameters. `NavigationSettings` is a `[Serializable]` section (not an asset) deriving from `UpgradeSettings` (which holds `enabled`) and adding `projectWideProfile` (renamed from `defaultProfile`, kept loadable via `FormerlySerializedAs`). It is stored in the package-wide settings (see below). `NavigationSettings.profile` is the single on/off check: it is null unless `enabled` is set **and** a profile is assigned. When it is null, `NavigationUpgrader` releases its target and does nothing, `TryResolve` returns false, and the Scene view visualizer shows Unity's own result. There is deliberately no built-in fallback profile. **The upgrade is off by default (opt-in).** `Editor/Navigation/NavigationSettingsDrawer.cs` supplies the section's body: the profile field with a **+** button to its right (the `Toolbar Plus` icon on a 22px `miniButton`, chosen by the user over a "New" text button; `CreateAddNew` also renders as a plain + in Unity 6, so it adds nothing). The + button opens `SaveFilePanelInProject` (default `Assets/Settings`), creates the profile, and assigns it. When enabled with no profile, a Warning is shown. The enable checkbox only flips `enabled` and never creates assets. Auto-creating a default profile at a fixed path was dropped because renaming or moving it led to duplicates. The body stays locked while disabled (the user's choice), so the flow is check, then +. Unchecking keeps the profile reference. Non-default profiles aren't consumed yet; they are meant for future per-area / per-group rules.
- Package-wide settings: `UIUpgraderSettings` (`Runtime/UIUpgraderSettings.cs`, internal ScriptableObject, namespace `Onion.UI`, one per project) holds one serializable `UpgradeSettings` section per upgrade (currently only `navigation`). New upgrades add a section field, a body drawer, and one `DrawSection` call, not a new asset. At runtime it is found via Preloaded Assets in builds and via `EditorBuildSettings` config key `com.onion.uiupgrader` in the Editor. `Editor/UIUpgraderSettingsEditor.cs` gives every upgrade the same layout: a URP-style header toggle, not a box (the user rejected a helpBox frame). The header is a full-width tinted band with 1px splitters, drawn like `CoreEditorUtils.DrawHeaderToggle`, which can't be referenced because render-pipelines.core isn't a dependency. It holds a foldout arrow, an enable checkbox, and a bold title (`SerializedProperty.isExpanded`; clicking the title toggles the foldout; enabling also expands). It also has a colored state badge, "● Upgraded" / "○ Unity Default". The user likes this wording because it carries the "upgrade" concept. The badge starts at `EditorGUIUtility.labelWidth`, so it lines up with the body fields' value column. Right-aligning it was tried and rolled back by the user. Upgrade/Revert buttons were tried and rejected by the user as clunky. Below the header is the feature's body, indented one level and locked with `DisabledScope` while disabled. There are no per-feature description lines and no on/off Info HelpBoxes; the user removed them. The same inspector is shown in **Project Settings > Onion > UI Upgrader** (`Editor/UIUpgraderProjectSettings.cs`, a `SettingsProvider` that hosts it via `CreateCachedEditor`). The page calls `DrawSettings()` directly. The asset's own inspector (`OnInspectorGUI`) adds an "Edit in Project Settings Window" button on top, which calls `UIUpgraderProjectSettings.Open()`. Double-clicking the asset does the same through an `[OnOpenAsset]` handler. `Editor/UIUpgraderSettingsProvider.cs` creates `Assets/Settings/Onion_UIUpgraderSettings.asset` on editor load if missing (skipped in batch mode). It also removes the pre-`UIUpgraderSettings` asset (`Onion_NavigationSettings.asset`, config key `com.onion.uiupgrader.navigation`) and its missing Preloaded Assets entry. Its values are not carried over, by the user's choice.
- This design intentionally differs from onion-scene-management's settings in these ways: the main asset is looked up by config key instead of scanning Preloaded Assets, `hideFlags` are not changed on the asset, and nothing is created in batch mode.
- The namespace `Onion.UI.Navigation` shadows the type `UnityEngine.UI.Navigation`, so files in it use the alias `UINavigation`.

## NavigationGroup

`Runtime/Navigation/NavigationGroup.cs` is a public, non-Selectable container component (requires a RectTransform). It only affects upgraded modes and does nothing while the upgrade is off. Explicit slots can't reference groups, and the user decided they don't need to.
- Scope: a Selectable belongs to the nearest enabled group on itself or its ancestors (`ScopeOf`), or to the root (null). Upgraded navigation only considers Selectables under the origin's scope (`IsChildOf`), including those inside its child groups. Groups have no rect of their own at runtime: an earlier version scored each child group as one rect (its RectTransform), which the user dropped because a RectTransform can differ from the area its members actually cover. Groups register themselves in a static list on enable.
- `boundary`: `Contain` (default, the user's choice) stops at the group's edge. `PassThrough` searches the parent scope when nothing is found inside, excluding everything under the group being left. Wrap-around happens inside the current scope first, so a wrapping group never passes through.
- Entering a group: when the picked Selectable lies in groups below the search scope, those groups are checked from the outermost inward, and the first usable `defaultSelectable` (active and interactable) wins; otherwise the picked Selectable itself. The result is written into the Explicit slot as a Selectable, so no re-selection happens (which would hit `EventSystem`'s "already selecting" guard). `TryResolve` has an overload that also reports the outermost group each direction enters, for the visualizer.
- Dropped on purpose, for now: anchor Selectables, group-to-group links, `selectOnEnable`, `restoreOnDisable`, remembering the last selection.

## Deferred optimizations

Not done yet, by the user's choice. `NavigationUpgrader` recomputes all four neighbors every `LateUpdate` while something is selected. That costs about 4n `GetLocalRect` calls per frame for n Selectables, each with 1 `GetWorldCorners` and 4 `InverseTransformPoint` native calls.
- Compute each candidate's local rect once per frame and share it across the four directions, instead of recomputing it inside every `FindNeighbor` call. This cuts the rect work to 1/4.
- Transform corners with `origin.transform.worldToLocalMatrix` fetched once and `MultiplyPoint3x4`, instead of calling `InverseTransformPoint` per corner. This leaves about one native call (`GetWorldCorners`) per candidate.
- Each Pass Through level repeats the whole candidate loop (`IsChildOf` checks and rects). Caching each candidate's rect per frame covers most of it.

## Known limitations

Also not addressed yet.
- One-frame lag: Unity's `Selectable.OnMove` searches at the moment of input, inside `EventSystem.Update`. The upgrader's result comes from the previous frame's `LateUpdate`. If a candidate becomes non-interactable in this frame's `Update` before input is processed, it can still be navigated to. `Selectable.Navigate` only checks `IsActive()`, not interactability. Candidate fix: move the work to an `Update` with a very low `[DefaultExecutionOrder]` so it runs before `EventSystem.Update`.
- Changing the selected Selectable's own `navigation` from a script while it is selected is lost. The upgrader overwrites it every frame from `_originalNavigation` and restores that old value on release.
